# Carrel × Codex 實際使用評估 — 2026-09-30

**基本工具選擇可用；優先改善預演結果與查詢介面。** 六個獨立 Codex session 都能從自然語言找到 Carrel，正確區分個人與專案；續接原 session 補公鑰也成功。沒有實際建立機器、網路、SSH key 或配額申請。

這輪是評估與改進建議，當時未修改或部署產品程式。後續修正、部署及同 prompt 重測見 [2026-10-01 結果](2026-10-01-codex-mcp.md)。

## 測試條件

- Codex CLI 0.159.2；沿用本機設定：`gpt-6-astra`、`github_copilot` provider、`xhigh`。
- 服務版本：commit `5afb545`；36 個一般成員工具、9 個僅管理員可見工具。
- 使用已登入的真實 Carrel MCP，帳號 `zyx1121`，可操作個人與 `iii-edge-ai` 專案租戶。
- 六個新 session 在 repository 外的空白工作目錄執行，避免讀取原始碼或舊對話提示答案；另續接其中一個 session。
- 每段 prompt 都明確限於查詢與 dry-run，禁止新增資源、配額申請、儲存公鑰、SSH 或直接 API 繞過 MCP。shell 使用 read-only sandbox。MCP 的 dry-run 限制由 prompt 與事後軌跡驗證；shell sandbox 本身不會限制 MCP 寫入。
- 共 **7 段 prompt、48 次 MCP 呼叫**，沒有 shell 操作。所有建立／掛接呼叫皆帶 `dry_run: true`。
- 每情境僅執行一次；耗時包含 CLI、MCP 啟動及模型推理，不是純 API 延遲。這不是跨模型的成功率基準。
- 未驗證實際 VM 啟動、套件安裝、SSH、服務發布、snapshot rollback 或管理員流程。

## 結果

| 情境 | 呼叫數 | 秒 | 結果 |
|---|---:|---:|---|
| 查個人及專案配額 | 3 | 39.8 | `whoami` 後查兩個租戶；數字正確 |
| Ubuntu + Docker，未提供公鑰 | 7 | 37.6 | 選 VM 正確；dry-run 被 SSH key 前置檢查擋下 |
| 專案 Docker VM，提供公鑰 | 7 | 54.1 | 正確指定專案、Ubuntu、4 vCPU／8 GiB／40 GiB，dry-run 成功 |
| 個人 16 vCPU／32 GiB 超額 | 6 | 41.7 | 實際取得 `quota_exceeded`；指出 CPU 與 RAM 都超額，沒有擅自送申請 |
| 兩台 Mininet VM + 私人網路 | 14 | 83.2 | 個別建立 dry-run 成功；掛 NIC 兩次 `not_found`，模型正確揭露未完成的部分 |
| 查實體容量及 GPU | 7 | 52.6 | 沒有把 quota 當硬體容量；但額外探測 resources 與建立 dry-run 都無助取得答案 |
| 同一 session 補公鑰繼續 Docker 預演 | 4 | 26.5 | 沿用先前配置，直接預演成功，沒有要求重新同意或註冊 |

共 7 次失敗呼叫：1 次預期的配額拒絕、2 次缺公鑰、2 次預演物件不存在、2 次未實作的 MCP resource discovery。這些原因不同，不宜直接當成模型錯誤率。

模型做得好的地方：Docker、Mininet、OVS 都選 VM；沒有把 Mininet 誤認為一定需要 nested KVM；個人／專案切換正確；平行查詢互不相依的資料；清楚區分成功預演與真實資源，也沒有編造 GPU 型號或實體容量。

## 優先修正

### P0：修正 dry-run 的回傳語意

**實測 bug：** `network_create(dry_run=true)` 成功預演一條網路，但 `quota_after.used.networks` 仍為 **0**，應為 **1**。模型若信任這個欄位，會算錯剩餘額度。[platform.py](../../src/carrel/platform.py) 的 network 分支驗證了 delta，回傳時卻重新讀取未變更的用量。

port、domain、snapshot 分支也有 dry-run 最後回傳目前用量的相同程式模式；本輪未對這三類進行實際情境測試，修正時應一併驗證增加與刪除方向。

另外，VM 預演回傳 `state: provisioning`、`created_at`、具體 VMID/IP/SSH 命令，容易被當成已配置。建議回傳 `state: planned`、`reserved: false`，並把暫定連線資訊標記為估計；不要暗示正在開機。

驗收：每個 mutation 的 dry-run 都回傳正確的 `quota_before / delta / quota_after`，且資料庫不變。

### P1：資源預演不應被缺公鑰完全擋住

兩次測試都因缺 SSH key，連容量檢查結果也拿不到。[platform.py](../../src/carrel/platform.py) 目前在 quota／admission 之前執行 `validate_keys`。

建議在 dry-run 中允許缺公鑰，繼續執行可完成的檢查，回傳 `requirements: [ssh_public_key]` 與 `ready_to_apply: false`。真正建立時仍要求有效公鑰；不需假金鑰、不需先儲存 key。

驗收：沒有 key 也看得到規格、quota delta、主機 admission 結果；實際建立仍拒絕缺 key。

### P1：新增一個整組資源的 `deployment_plan`

兩台 VM 的獨立 dry-run 都回傳同一組 `vmid=10400 / ip=10.200.4.10 / SSH port=20040`。接著兩次 NIC 預演都失敗，因為先前預演沒有建立物件。模型雖有解釋，但現在無法證明整組部署可行。

新增唯讀的 `deployment_plan`：一次接受多台 VM、網路與 NIC 關係，使用暫存的規劃狀態，合計 quota／capacity，並支援尚未建立物件的符號引用。預演不預留正式 VMID/IP/port。

先實作唯讀規劃即可；apply 可沿用現有明確、具型別的 mutation tools，不必一次加入大型交易引擎。

驗收：兩台各 6 vCPU 對 8 vCPU 租戶須因合計超額失敗；兩台 2 vCPU 加私人網路可完整預演含 NIC，配置不互相重複，無資料庫寫入。

### P1：補上可見能力與容量摘要

一般成員看不到管理員的 `node_list`。GPU／硬體問題因此觸發無用的 `resources/list`、`resources/templates/list` 探測，回覆 `Method not found`；之後又用缺 key 的 VM dry-run 嘗試探測容量。

- 在 `whoami` 或資源目錄中回傳目前支援的能力與可見範圍，例如 GPU 配置、客製映像、整組預演是否支援。
- 新增成員可用的 `capacity_get`，僅提供總量／可配置摘要及資料時間，避免暴露其他租戶機器明細；明確區分實體容量、CPU 超配政策、租戶 quota。
- `gpu_allocation_supported: false` 不等同「主機沒有 GPU」。功能未支援與硬體庫存未知應分開呈現。
- 若 server 沒有 MCP resources，提供空 discovery 回覆或清楚描述只有 tools，可減少無意義失敗。

## 值得合併、隱藏或刪減的部分

1. **擴充 `whoami`，不用再加一支重複 overview tool。** 每個可見租戶一次帶 `used / limit / remaining`、預設租戶與必要能力。目前只查兩個租戶 quota 就要 3 次呼叫；`quota_get` 可保留做指定租戶刷新。
2. **合併 `images_list`、`sizes_list` 為 `catalog_get`。** 同時回傳映像、規格、單位、支援能力。既有名稱先保留相容期；新的 agent 介面優先只暴露 catalog。
3. **暫時隱藏 `images_gb` 配額。** 首次 quota 回答列出 20 GB「映像儲存空間」，但目前沒有 image upload/import 工具，usage 也沒有自訂映像的計量路徑。先從使用者介面隱藏，保留資料庫欄位至未來功能實作，避免誤以為已可使用。
4. **去掉預演回傳中的假執行狀態與多餘內部欄位。** 預設回覆聚焦人類能用的名稱、規格、預演結果、連線預估及配額；MAC、內部 host index、tenant serial 等可放進可選 details。
5. **減少每次 dry-run 後的重複查詢。** Docker 成功後又查清單與 quota；續接公鑰後又查清單、quota、key。可信、一致的 preview contract 可省下 2–3 次呼叫。測試回合受明確的「不得變更」限制影響，正式使用未必每次都出現這些驗證。
6. **明確標示 MiB／GiB。** schema 使用 `memory_mb`、`disk_gb`，執行端按二進位容量處理，但模型數次寫 MB／GB。參數 description 直接註明單位，降低不一致。

目前沒有證據需要刪掉 VM、網路、port、domain、snapshot 的基本操作。這輪真正造成卡關的是 preview 與查詢能力，不是模型分不清動詞。完整 destructive／recovery 工具是否好用，需要後續使用隔離測試租戶與真實測試 VM 驗證。

## 建議實作順序

1. 修 `quota_after`、預演狀態、缺 key 的預演流程。
2. 精簡 quota／catalog 回覆，加入明確能力描述；隱藏未實作的映像配額。
3. 補 `capacity_get` 與 `deployment_plan`。
4. 用相同 prompt 重跑比較工具往返與結果，再以隔離 VM 驗證建立→SSH→HTTPS→快照→清理的完整生命週期。
